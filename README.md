# EPD Sender · 墨水屏传图网页

一个**纯静态**的单页工具：在手机或电脑上打开网页 → 选图 → 框选取景 → 选颜色模式 → 通过 **Web Bluetooth** 连接 CH584M 墨水屏设备 → 发送。

- 无后端、无构建步骤、不引任何 CDN，断网也能打开（只要页面已在本机/已加载）
- 目标分辨率：横屏 **720×480** / 竖屏 **480×720**（可切换）
- 颜色模式：**64 色**（实测调色板）/ **6 色** / **黑白**
- 支持整体旋转、亮度/对比度、抖动开关、自由缩放平移取景
- 导出 4bpp 索引数据（`.bin`）方便后续固件联调

## 三、手机上怎么用

1. 用 **Chrome（安卓）** 或 **Edge** 打开上面的 https 地址
2. 点「选择图片」（或把图片拖进画布）
3. 拖动 / 双指缩放把想显示的部分放进白色取景框；横/竖屏切换在右侧「取景」
4. 选颜色模式；照片类建议开「抖动」，线稿类可以关掉
5. 点「连接设备」→ 列表里选名字以 **EPD-CH584** 开头的设备
6. 在「文本内容」里输入文字，点「发送到屏幕」

> 可以把这个网址「添加到主屏幕」，用起来和 App 差不多。

### iPhone / iPad

Safari **不支持** Web Bluetooth，需要装 **Bluefy** 这类支持 Web Bluetooth 的浏览器再打开同一网址。安卓不会有这个问题。

## 四、参数说明

| 参数 | 说明 |
|---|---|
| 取景方向 | 横屏 720×480（与屏幕物理方向一致）/ 竖屏 480×720 |
| 缩放 | 0.2×~6×，1× = 图片刚好铺满取景框；滚轮、双指、滑块都可 |
| 旋转 | -180°~180°，也可以 ±90° 快捷按钮 |
| 抖动 | Floyd–Steinberg 误差扩散。开：过渡自然但颗粒感强；关：色块干净但会出现断层 |
| 亮度/对比度 | 先调这两个再量化，效果比后期改色好 |
| 颜色模式 | 64 色用固件里实测的 8×8 色表（索引 = `(色相<<3)|明度`）；6 色用面板原生黑/白/红/黄/蓝/绿；黑白即 1bit |

## 五、数据格式（给后续固件联调用）

- 每像素 4 bit，索引 0~63 即 64 色调色板序号
- 一帧 = `W/2 × H` 字节：720×480 → **172800 字节**；480×720 同样 172800 字节
- 字节内**高 4 位 = 左边的像素**，低 4 位 = 右边的像素
- 点「下载 .bin」可以直接拿到这串数据，拿去和固件里的 `pack_plane()` 对照

## 六、已知限制

- 固件当前只实现了「收文本 → 上屏」，**图像协议还没上**，所以「发送图像」按钮是灰的。等固件加了图像接收特征值，这里的 `.bin` 可以直接按 20 字节分片灌进去。
- 一次写 20 字节是 BLE 默认 MTU 的限制；固件以后把 MTU 提到 247，这个页面只需改一个常量。
- 整屏刷新约 70 秒（三相同步刷新，物理限制），发送后请耐心等待，不要断电。

## 七、排错

| 现象 | 原因 / 处理 |
|---|---|
| 点连接没反应、按钮灰 | 页面不是 HTTPS，或浏览器不支持（见顶部提示） |
| 弹窗里找不到设备 | 确认设备在上电广播、名字以 `EPD-CH584` 开头；打开「找不到时列出所有设备」再试 |
| 连上但发送失败 | 特征值不对：先把日志贴出来，看是 `0xFFE1` 还是回退到了 `0xFFE3` |
| 发送成功但屏幕没反应 | 固件要求一次写入不超过 20 字节且中间留间隔，页面已按 30 ms 限速；若仍无反应，检查串口日志 |
| 画面颜色发灰/发花 | 抖动开太强，或这张图本身色域超了；试试关抖动、调对比度 |
| iOS 上完全没有蓝牙选项 | Safari 不支持，用 Bluefy |

## 八、安全与隐私

图片全部在浏览器本地处理，不上传任何服务器；页面本身只是一个静态文件。


## 九、图像传输（固件 v7 起）

「发送图像」按钮走的是 BLE 图像协议，不再依赖纯文本：

| 步骤 | 手机发出的字节 | 设备回的通知（0xFFE4） |
|---|---|---|
| 连接后 | — | `B1 lo hi`：协商后的 ATT MTU |
| 开始 | `49 00`（`'I'` + mode 0） | `B0 01`：可以发数据了 |
| 平面 1 | `44 …`（`'D'` + 最多 MTU-4 字节）× N，再 `45`（`'E'`） | `B0 01`：第二平面可以发 |
| 平面 2 | 同上 | `B0 03`：整屏刷新完成 |

- 每像素 4 bit，一个平面 = 480 行 × 360 字节 = **172800 字节**，两个平面（色相 + 明度）共 345600 字节
- 48 色是三次刷新的时间抖动：第一相定色相曲线、第二相推进、第三相定明度；所以中途设备会回 `B0 01` 让你发第二个平面
- 6 色 / 黑白也走同一条 48 色管线（它们本来就是 48 色里的锚点色），出图时间一样，好处是只有一条代码路径
- 实测（假设备联调）：MTU 247 时每次 243 字节、共约 1424 包，两个平面各 172800 字节分毫不差
- 传图期间请让页面保持前台、别锁屏。中途断链就重连再点一次，设备会丢弃那半截平面

## 十、v10：刷新心跳、空闲看门狗、MTU 查询、6 色快传

v9 之前网页只在"收到状态通知"时才知道设备活着，而 48 色是**三次刷新**的波形，第一次平面发完后要连刷两相（每相约 55 秒），中间两分多钟一条通知都没有，页面会把设备当成失联。v10 这样解决：

| 改动 | 说明 |
|---|---|
| 刷新心跳 | 固件每 1 秒发 `B2 FF <阶段>`，页面显示"屏幕刷新中：刷新相1"之类的实时阶段 |
| 空闲看门狗 | `waitAny(…, 总超时, 空闲超时)`：总超时 420 秒，但**连续 90 秒没有任何上报**才判失联 |
| MTU 查询 | 连上后主动发 `4D`（`'M'`），设备立刻回 `B1 lo hi`；不再依赖"连上就推"那一次，不会退化成 19 字节分包 |
| 6 色 / 黑白快传 | 选 6 色或黑白时发 `49 01` / `49 02`，单平面单相刷新，约 **三分之一** 的时间 |

### 为什么 64 色要三分钟

64 色不是空间抖动而是**时间抖动**，一帧要刷三次：

1. 发色相平面 → 刷相 1（约 55 s）
2. 换波形 2 → 刷相 2（约 55 s）
3. 发亮度平面 → 换波形 3 → 刷相 3（约 55 s）

前两次刷新必须夹在两个平面之间，所以"传完图到屏幕开始刷新"中间那两三分钟是面板物理时间，不是卡住。想快就选 **6 色**或**黑白**（单相，约 20 s + 一次刷新）。

## 十一、v12：连接参数、旧固件误报、长刷新等待

| 现象 | 原因 | v12 的处理 |
|---|---|---|
| 传完图要等 3 分钟屏幕才动 | 固件请求 15 ms 连接间隔的代码被一个 `if (timeout < 1000)` 守卫挡住，请求一次都没发出去，空口速率只有约 1 KB/s | 去掉守卫，连上 1 秒后开始请求，每 5 秒一次共 6 次；页面会打印实际的「间隔 xx ms · 监督超时 xx s」 |
| 刚连上就报"板子里是旧固件" | 3 秒判定只看"状态通知计数"，而设备的 MTU 通知不算状态 | 改成看"任何通知"的计数，并把宽限放到 8 秒；之后只要收到任何通知就自动撤销该提示 |
| 64 色传图报"等设备超时" | 页面等"可以发数据"只给 30 秒，而 64 色初始化（载入波形 + 5000 ms 静置 + 面板上电）实测要 6~54 秒 | 等 ARMED 放宽到 120 秒 / 45 秒无消息；等平面完成放宽到 600 秒 / 120 秒无消息 |
| 刷到一半设备掉线 | 还没定位到根因（怀疑刷屏时板子复位） | 设备每次上报 MTU 都会带上自己的运行秒数；重连后页面若发现秒数变小，会直接打印「⚠ 设备重启过」 |

**烧录后请务必 `Ctrl+F5` 硬刷新页面**，否则浏览器会用缓存里的旧 `app.js`。
